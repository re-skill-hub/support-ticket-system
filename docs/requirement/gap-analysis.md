# Gap analysis: requirements vs. this implementation

This records every place the running system diverges from the project's source requirements, and how each divergence was resolved. It draws on three source documents opened across two passes: `Design Document.docx` (the original architecture/tech-stack brief), `epic-user-story.txt` (8 epics of functional acceptance criteria), and `ux-design-consideration.txt` (personas, UX journeys, interaction patterns). It extends — rather than repeats — the "Scope notes" section at the bottom of the root `README.md`, which lists deliberate omissions from the as-built system's own point of view; this document instead starts from the requirements and works forward.

Snapshot date: 2026-10-01.

## Resolution categories

- **Implemented** — the gap was closed; the requirement is now met.
- **Partially implemented / kept as an improvement** — either the core mechanism exists but a specific polish item from the source doc wasn't built, or the running system deliberately does something more capable than a doc's generic template describes and was left as-is rather than reverted to match it.
- **Documented, out of scope** — the requirement has no current consumer or use case in this system, was descoped for cost (this runs on a free/trial Azure subscription plus local Docker Compose), or a source doc marks it explicitly as future work.

## Architecture

| Requirement | Current state | Resolution |
|---|---|---|
| Single ASP.NET Core Web API, single SQL Server database, Repository pattern over EF Core | Three independently deployable microservices (TicketService, ResponseService, NotificationService), one database per service, controllers use EF Core directly with no repository layer | **Partially implemented / kept as an improvement.** The design doc's own architecture section calls for "Microservices"; database-per-service and direct EF Core usage are the more idiomatic way to realize that, and a repository layer over EF Core (already a repository abstraction) would add indirection without behavioral benefit. |
| `PUT /tickets/{id}/comment` — comments as a sub-resource of the ticket, no event bus | Comments/replies live in a separate ResponseService; TicketService, ResponseService, and NotificationService communicate only via RabbitMQ events (`TicketCreated`, `TicketStatusChanged`, `ResponseAdded`), with no synchronous inter-service calls | **Partially implemented / kept as an improvement.** This is the direct consequence of the microservices decision above — a shared "comment" endpoint on TicketController isn't possible once responses own their own service and database; the event bus is what keeps the two consistent without a distributed transaction. |
| Azure DevOps pipeline → Azure Kubernetes Service (AKS) | A real Azure DevOps org/pipeline deploys to a real AKS cluster | **Implemented.** See "CI/CD and deployment" below. |
| (Not in the original design doc — added during hardening) An API gateway/BFF in front of the three services instead of nginx path-based routing, previously listed below as a recommendation | `services/ApiGateway`, a YARP reverse proxy with active health-checked routing and the same shared exception handling as the backend services | **Implemented.** `client/nginx.conf` routes every `/api/*` call through the gateway in all three environments (Docker Compose, local Kubernetes, AKS) — not just built alongside the old direct routing. Verified end-to-end (login, an authenticated call, and the full Playwright suite) before considering this done. See `docs/distributed-resilience.md`. |

## Distributed exception handling & fault tolerance

Not tied to a specific requirement in the source docs — a dedicated hardening pass requested directly, covering both the .NET backend and the Angular frontend. Full detail (what, why, code locations) is in `docs/distributed-resilience.md`; this table is the gap-analysis-style summary.

| Area | Current state | Resolution |
|---|---|---|
| Exception handling consistency | Every service threw raw framework exceptions for both business-rule violations and bugs, with no shared way to tell them apart | **Implemented.** Shared `AppException` hierarchy (`NotFoundException`/`ConflictException`/`BusinessRuleException`/`ForbiddenException`/`ProjectionNotReadyException`) + a `GlobalExceptionHandler` (`IExceptionHandler`) mapping each to a `ProblemDetails` response, plus specific handling for `DbUpdateConcurrencyException` (409, previously fell through to a generic 500) and client-aborted requests (logged quietly instead of alarming as unhandled). |
| MassTransit fault handling | A single flat 3×5s retry, identical across all three services, no dead-letter visibility | **Implemented.** Tiered handling: exponential immediate retry scoped to transient `AppException`s only, a circuit breaker, and a grep-able log marker on every dead-lettered message. Delayed redelivery (a fourth tier) is implemented but gated behind a config flag pending a RabbitMQ plugin install — see "Scope for further improvement." |
| Outbound-call resilience | `SmtpEmailSender` had no timeout at all; event publishing after a DB commit had no retry | **Implemented.** Polly pipelines (`"smtp"`, `"publish"`) via `Microsoft.Extensions.Resilience`; a publish failure after commit is logged Critical and surfaced as a clear 503 rather than an opaque 500 (the underlying non-atomicity — no transactional outbox — is a documented, not remediated, residual risk). |
| API gateway | See the Architecture table above | **Implemented** — live routing path in every environment. |
| Distributed tracing | No correlation beyond app-level logging | **Implemented, backend only.** OpenTelemetry SDK in every service (console exporter; OTLP hook ready but no backend stood up). |
| Angular error handling | Global `ErrorHandler` not overridden (template/binding errors only ever reached the console); no request timeout; 401 always said "session expired" even for a request that was never authenticated; a real Angular bug where a native `<select>`'s value silently failed to update | **Implemented.** See `docs/distributed-resilience.md` for the interceptor chain, the `GlobalErrorHandler`, the offline/service-unavailable UX, and the `<select>` bug fix (found and fixed via E2E investigation, not originally in scope — the role-change UI was silently reverting to the wrong value while the backend had actually saved the correct one). |
| CI/CD deploy safety | Deploy-stage conditions only checked "not a PR build," which a manually-queued run against an unmerged branch could bypass | **Implemented.** See "CI/CD and deployment" below. |

## Frontend framework and tooling

| Requirement | Current state | Resolution |
|---|---|---|
| Angular 18, NgModules (e.g. `customer.module.ts` / `support.module.ts`), Bootstrap | Angular 22, standalone components throughout (no NgModules), Bootstrap 5 + `@ng-bootstrap/ng-bootstrap`, feature-folder structure (`src/features/*`, `src/core/*`, `src/shared/*`) | **Implemented, with improvements kept.** Bootstrap now matches the design doc directly (an earlier iteration of this system used Angular Material instead; it was replaced with Bootstrap 5 + ng-bootstrap — `NgbModal` for dialogs, `NgbPagination` for tables, `NgbCollapse` for the responsive nav/sidebar — plus Bootstrap Icons and Inter as baseline visual polish). Standalone components and the feature-folder structure are kept as improvements over the doc's NgModule split: standalone components have been Angular's own recommended default since v16, and NgModules are legacy rather than current best practice. |
| Jasmine/Karma test runner | Vitest, via Angular's `@angular/build:unit-test` builder | **Partially implemented / kept as an improvement.** This is the Angular CLI's current default for new projects, replacing Karma/Jasmine; behavior (describe/it, `expect`) is equivalent, tooling is faster and simpler to run in CI (single non-interactive pass under `CI=true`, no headless-Chrome dependency). |
| Single environment, presumably with a dev/prod split implied by "Web App (Angular)" as a standard SPA deployment | One `environment.ts`, no `angular.json` `fileReplacements`, one relative `/api` path proxied by nginx straight through to the API Gateway (Docker Compose/k8s/AKS) | **Documented, out of scope.** The relative `/api` path works identically in every environment because nginx and the gateway both do path-based routing rather than the Angular app needing environment-specific base URLs. Introducing a dev/prod split would need a real reason (e.g. different backend hosts) that doesn't currently exist. Left as a known limitation of the "single relative API path" decision, not a new one. |

## Ticket fields and filtering

| Requirement | Current state | Resolution |
|---|---|---|
| Tickets have Priority and Category, filterable in the queue/list views | `Ticket` had neither field; nothing to filter on | **Implemented.** `Priority` (`Low`/`Medium`/`High`/`Urgent`) and `Category` (`General`/`Technical`/`Billing`/`Account`) added to the `Ticket` entity (new EF Core migration), `CreateTicketRequest`/ticket response DTOs, and `GET /api/tickets`'s existing `?status=` filter gained sibling `?priority=`/`?category=`/`?customerId=`/`?fromUtc=`/`?toUtc=` filters (date range inclusive on `CreatedAtUtc`). Mirrored on the frontend: all fields on the create-ticket form / agent-queue filter bar, both status and priority displayed as table columns with a `PriorityChip` component (matching the existing `StatusChip` pattern), and `<input type="date">` controls converted to UTC day-boundary ISO strings at the point of the API call. `TicketService.getAll()` was reshaped from positional args to a `TicketQueryFilters` object to keep the growing parameter list manageable. |
| Epic 4 (triage/manage intent) — assign-to-other-agent | Backend only supported self-assignment (`PATCH /tickets/{id}/assign` with no body); no way for staff to hand a ticket to a colleague or unassign it | **Implemented.** The assign endpoint now accepts an optional `agentId` (`null` unassigns); a new `GET /api/tickets/agents` endpoint (staff-only, name-only `{id, fullName}` projection via `UserManager.GetUsersInRoleAsync`) feeds a staff picker dropdown on the ticket-detail page, added alongside the existing "Assign to me" shortcut. Kept off `UsersController` deliberately — that controller stays Admin-only for the full user-management roster (email, active status, role changes); the new endpoint is a minimal staff-visible slice on `TicketsController`, which is already staff-accessible. |
| Epic 4.2 (literal AC: "if the API call fails, an error message is displayed and the previously displayed status is preserved") | `ticket-detail.ts`'s `applyStatusChange()` had no `error` handler — a failed status PATCH left the status `<select>` on the attempted value instead of reverting | **Implemented.** An `error` callback now reverts `statusControl` to the ticket's last-known status on failure; the existing global error-toast interceptor still surfaces the failure message, so no duplicate error-handling was added. |
| Ticket/response list pagination (`GetAll`/`GetMine`, `GetByTicket`) | Client-side pagination over the full filtered result set | **Documented, out of scope.** Adding server-side `PagedResult<T>` would only be safe if `ticket-list.ts`'s client-side title search and `ticket-queue.ts`'s client-side column sort also moved server-side — otherwise search/sort would silently only see one page instead of the full result set, a real UX regression disguised as a scalability improvement. That's a substantially larger, riskier change than the current data volumes justify; revisit if ticket counts grow large enough for this to matter in practice. |

## Account, profile, and password recovery

| Requirement | Current state | Resolution |
|---|---|---|
| Epic 1.4 (View User Profile) — `GET /users/{id}` should let a user view **their own** profile; UX doc's "Forgot password?" link | `GET /api/auth/me` already existed but had no frontend page; `AddIdentityCore<ApplicationUser>` in `Program.cs` had no `.AddDefaultTokenProviders()`, so password-reset tokens couldn't be generated at all | **Implemented.** `.AddDefaultTokenProviders()` added; `POST /api/auth/forgot-password` and `POST /api/auth/reset-password` added to `AuthController` (forgot-password always returns 200, no email-existence leak, reuses the existing `"auth"` rate-limit policy); new `Services/EmailSender.cs` sends via SMTP. New `client/src/features/auth/forgot-password/` and `reset-password/` pages, wired into `app.routes.ts` as anonymous routes; `login.html` links to forgot-password. New `client/src/features/profile/` read-only page at `/profile`, linked from the nav bar (replacing the previous static, unlinked full-name span). |
| Email delivery for password resets, cost-constrained | Password-reset emails need somewhere to land without a paid provider | **Implemented via Mailpit.** Self-hosted single-container SMTP catcher (MailHog successor) added as a `docker-compose.yaml` service and a local-Docker-Desktop-`k8s/08-mailpit.yaml` manifest (no ingress/public exposure, negligible resource cost). `Smtp__Host/Port` and `Frontend__BaseUrl` are config-driven, so swapping to a real provider later is a config change only. **The `k8s/azure-dev/` AKS overlay does not deploy Mailpit** — see "Scope for further improvement" below. |
| Real email delivery to an actual inbox (SendGrid / Azure Communication Services) | Mailpit only | **Documented, out of scope.** Descoped for cost on a free/trial Azure subscription; Mailpit proves the forgot/reset-password flow end-to-end without a paid provider, and the SMTP config keys are the documented swap-in point. |
| `GET /users/{id}` — retrieve another user's details (Admin) | `UsersController` (Admin-only) exposes the full user-management surface: `GET /api/users` (paginated, role-filterable), `GET /api/users/{id}`, `POST /api/users` (create with any role), `PUT /api/users/{id}/role`, `PATCH /api/users/{id}/status` (activate/deactivate) | **Implemented.** This is net-new scope beyond the design doc (which only ever specifies Customer + Support Staff, not a third Admin role), added at the user's request. The admin user-management screen (`/admin/users`) is the real consumer this endpoint was previously missing — see `README.md` for the third role and the `INITIAL_ADMIN_*` bootstrap. |

## Scope for further improvement

Forward-looking items — not closed gaps against a specific requirement, but real follow-ups worth tracking before or after a production push.

- **Architecture diagrams — combined and extended.** The two previous SVGs (`architecture-diagram.svg`, `architecture-diagram-e2e.svg`) were combined into one `docs/architecture-diagram.svg` covering the full app + CI/CD + AKS picture, showing the API Gateway inline as the live routing path, plus a new `docs/architecture-diagram-local.svg` specifically for the Docker Compose topology.
- **Local Kubernetes Service ports — fixed.** `k8s/04`–`k8s/06`'s Services only exposed a "debug" port (5101/5102/5103, matching the design-doc-era convention of hitting each service directly from the host) and never the container's actual port (8080) — meaning nginx, running *inside* that same cluster, could never actually reach any backend through its Service; only Docker Compose and AKS (whose Services both use 8080) worked. Surfaced while wiring up the API Gateway cutover below. Fixed by giving each local Service both ports.
- **`client/nginx.conf` `/api/users` routing — fixed.** The three proxy regexes previously didn't match `TicketService`'s `UsersController` at `/api/users` (only `auth`/`tickets` were routed there), so Admin user-management calls fell through to the Angular SPA catch-all in both Docker Compose and local Kubernetes. Fixed by broadening the first regex to `^/api/(auth|tickets|users)(/|$)`.
- **`README.md`'s local-agent seed claim — corrected.** The seed logic in `DbSeeder.SeedLocalAgentAsync` has no environment check at all; it runs whenever `LocalAgent:Email`/`LocalAgent:Password` config values are non-empty, regardless of `ASPNETCORE_ENVIRONMENT`. The AKS overlay (`k8s/azure-dev/workloads.yaml`) wires these from a Key-Vault-backed secret populated by the Azure DevOps pipeline, so the seeded support-agent account is genuinely active on the live AKS deployment too — not restricted to local Docker Compose as previously documented.
- **AKS overlay has no Mailpit/SMTP deployment.** Password-reset emails have no delivery path once deployed to AKS (Mailpit only exists in `docker-compose.yaml` and the local Docker-Desktop `k8s/08-mailpit.yaml`); forgot/reset-password on the live demo will accept the request (still returns 200) but the email is never delivered anywhere reachable. A future pass could add a Mailpit deployment to `k8s/azure-dev/` (still no public ingress needed — port-forward for review) or swap in a real provider via the existing `Smtp__*` config keys.
- **RabbitMQ delayed-message-exchange plugin not installed.** The MassTransit delayed-redelivery tier (`docs/distributed-resilience.md`) is implemented in code but gated behind a config flag until this broker plugin is installed on both the local and AKS RabbitMQ instances.
- **K8s base manifests (`k8s/00`–`k8s/09`) have no resource requests/limits on the app Deployments.** The `k8s/azure-dev` Deployments already have them; the local/Docker-Desktop manifests don't.
- **Azure DevOps deploy-approval gate is disabled.** An Approval check exists on the `support-ticketing-dev` environment (created 2026-09-27) but was subsequently turned off, so `DeployDev` runs unattended today. Re-enabling it is a one-click portal action.
- **GitHub branch protection `enforce_admins` is off on `main`.** The required review + status check exist, but don't apply to admin/write-bypass-eligible accounts. Every change that has actually landed on `main` went through a real reviewed PR (#1–#8) — this is a closeable gap, not a known-exploited one — but flipping it is a workflow change (it also restricts the admin accounts' own ability to push directly) that needs a decision, not just a code change.
- **Other pre-existing, still-valid recommendations** (not re-litigated in detail here — see `docs/azure-deployment.md` and `docs/ci-cd-pipeline.md` for context): managed Azure SQL / Azure Service Bus instead of self-hosted SQL Server/RabbitMQ inside the cluster; JWT refresh-token rotation (current sessions are cookie-based with no refresh flow); tightening the `ci-deployer` / ACR service-connection scope further as the project matures past a single dev environment.
